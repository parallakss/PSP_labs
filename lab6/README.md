## 1. Введение в промисы (Promises) и Fetch API

Ранее для выполнения сетевых запросов (HTTP) использовался устаревший объект `XMLHttpRequest` (XHR), который работал на основе функций обратного вызова (колбеков). Это часто приводило к проблеме "Callback Hell", когда код становился нечитаемым из-за глубокой вложенности.

В рамках работы весь сетевой слой был переписан на использование **Promise** и **Fetch API**.
Промис (Promise) — это объект, представляющий результат успешного или неудачного завершения асинхронной операции. Он может находиться в трех состояниях: *pending* (ожидание), *fulfilled* (успешно выполнено), *rejected* (ошибка).

В клиентском коде кораблестроительного производства получение данных теперь выглядит так (с использованием синтаксического сахара `async/await` поверх промисов):

```javascript
async function fetchStocksData() {
    try {
        // Fetch возвращает Promise. Await ставит код "на паузу" до его разрешения
        const response = await fetch('http://localhost:3000/stocks');

        if (!response.ok) {
            throw new Error(`Ошибка HTTP: ${response.status}`);
        }

        // response.json() также возвращает Promise
        const data = await response.json();
        return data; // Возвращаем массив классов кораблей
    } catch (error) {
        console.error("Промис был отклонен (rejected):", error);
        return [];
    }
}
```
Такой подход делает асинхронный код визуально похожим на синхронный, что значительно упрощает его чтение и поддержку.

## 2. Сборка проекта с помощью Bundler

Наш проект фронтенда разбит на множество ES6 модулей (например, `add/main.js`, `add/pages/product/index.js`, `add/components/product-card/index.js`). Изначально браузер загружал каждый файл отдельным сетевым запросом. Это крайне неэффективно для крупных проектов.

Для решения этой проблемы был внедрен инструмент сборки — **Bundler** (например, Webpack). Сборщик берет файл-точку входа (`main.js`), анализирует все деревья `import / export` и склеивает (бандлит) весь JavaScript-код в один единственный минифицированный файл (обычно `bundle.js`).

Была произведена инициализация сборщика в папке фронтенда и настройка конфигурации `webpack.config.js`:
```javascript
const path = require('path');

module.exports = {
    entry: './add/main.js', // Точка входа
    output: {
        filename: 'bundle.js',
        path: path.resolve(__dirname, 'dist'), // Папка для собранного бандла
    },
    mode: 'production' // Минификация и обфускация кода
};
```
После выполнения команды `npm run build` все файлы компонентов объединились в папке `dist/`, готовые к развертыванию на боевом сервере.

## 3. Развертывание статики на сервере Express

До этого момента фронтенд (HTML/CSS/JS) и бэкенд (Express API) запускались на разных портах (например, через Live Server). В реальных проектах сервер часто сам отдает клиентские файлы пользователю.

Собранная папка `dist/` (с `bundle.js` и `main.html`) была скопирована в директорию бэкенда `example-express/public/`. В `index.js` сервера был добавлен встроенный middleware `express.static`, который позволяет серверу автоматически отдавать статические файлы:

```javascript
const express = require('express');
const path = require('path');
const app = express();

// Настраиваем раздачу статики из папки public
app.use(express.static(path.join(__dirname, '../public')));

// Роуты API
app.use('/stocks', stocksRouter);
```
Теперь при переходе по адресу `http://localhost:3000/` пользователь получает интерфейс приложения, который уже сам делает запросы к `http://localhost:3000/stocks`.

## 4. Стратегия работы с Git-ветками

Согласно заданию, была реализована строгая политика версионирования в Git:
1. **Ветка лабораторной №6 (`lab6`)**: В этой ветке хранится весь "сырой" исходный код проекта. Здесь лежат отдельные файлы компонентов (`ProductCardComponent.js`, `MainPage.js`), конфигурации Webpack и несжатые стили. Исходный код необходим разработчикам для продолжения работы.
2. **Ветка лабораторной №4 (`lab4`)**: Сюда добавляются **только** результаты работы сборщика (папка `dist` / файлы `bundle.js`).

Процесс переноса:
```bash
git checkout lab6
npm run build # генерируется bundle.js
git checkout lab4
# Копирование bundle.js из ветки lab6
git checkout lab6 -- dist/bundle.js
git commit -m "Add compiled frontend bundle"
```
Это разделяет исходники и артефакты сборки по разным логическим веткам репозитория.

## 5. Дополнительное задание: Управление сложными таймерами (setTimeout)

В рамках работы я спроектировал и полностью реализовал уникальную систему управления отложенными событиями (таймерами) для карточек классов кораблей. Логика инкапсулирована в компоненте `ProductCardComponent` и содержит 3 новые кнопки: "Удалить через 50 сек", "Удалить сразу" и "Проверить таймер".

Особенности технической реализации:

1. **Отложенное удаление и защита от потери данных (Persistence)**
   Функция запускает `setTimeout` на 50 000 мс (50 секунд). Чтобы таймер не "сбросился" в случае, если пользователь случайно обновит страницу в браузере (F5), время окончания таймера сразу же записывается в долговременную память браузера `localStorage`:
   ```javascript
   const storageKey = `delete_timer_${data.id}`;

   delayBtn.addEventListener("click", (e) => {
       if (!this.deleteTimer) {
           e.target.innerText = "Удаление через 50с...";
           ProductCardComponent.activeTimers.add(data.id); // Запись в глобальное состояние
           localStorage.setItem(storageKey, Date.now() + 50000); // Сохраняем Timestamp
           this.deleteTimer = setTimeout(performDelete, 50000);
       }
   });
   ```
   При рендеринге карточки конструктор проверяет, есть ли в `localStorage` активный таймер. Если он там есть и время еще не вышло — `setTimeout` пересоздается на остаток времени. Если время вышло, пока страница была закрыта — карточка удаляется немедленно.

2. **Немедленное удаление и очистка памяти**
   Кнопка «Удалить сразу» не просто стирает карточку. Она обязана предотвратить срабатывание "брошенного" таймера. Для этого вызывается системная функция `clearTimeout`:
   ```javascript
   document.getElementById(`del-btn-${data.id}`).addEventListener("click", () => {
       if (this.deleteTimer) {
           clearTimeout(this.deleteTimer); // Убиваем запущенный процесс
           this.deleteTimer = null;
       }
       performDelete(); // Очистка localStorage и вызов callback-а удаления
   });
   ```

3. **Глобальная проверка состояния таймеров**
   Для кнопки "Проверить таймер" в классе `ProductCardComponent` было объявлено статическое (глобальное для всех объектов) свойство `static activeTimers = new Set();`. Это позволяет любой карточке узнать, запущены ли процессы удаления у других карточек в системе:
   ```javascript
   document.getElementById(`action-btn-${data.id}`).addEventListener("click", () => {
       // Проверяем размер глобального Set (коллекции уникальных ID)
       const hasAnyTimer = ProductCardComponent.activeTimers.size > 0;
       actionListener(data, hasAnyTimer);
   });
   ```
   Этот сложный функционал демонстрирует глубокое понимание жизненного цикла компонентов, асинхронности в JS (Event Loop) и работы с Browser API.
